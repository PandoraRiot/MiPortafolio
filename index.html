Thesis · Research

DCE-MRI Breast Cancer Classification

Medical AI
Computer Vision · PyTorch

A Deep Learning pipeline for breast-lesion classification from Dynamic Contrast-Enhanced MRI, built with a patient-level-safe methodology: stratified splits, cross-validated architecture comparison, and a fully isolated holdout test.

Stack — PyTorch · ResNet / EfficientNet / MobileViT · Docker · scikit-learn metrics

What it does

Processes temporal DCE-MRI sequences (PRE / EARLY / LATE contrast phases) to identify malignancy biomarkers in breast lesions, as an undergraduate thesis in applied medical imaging.

Engineering principles

Leakage-safe patient-level splitting, reproducible stratified partitioning, and a strict separation between model-selection data and the final holdout — the same discipline a clinical ML pipeline needs before it can be trusted.

Pipeline

ROI dataset (BREAST_ROI_FULL.csv)
  → DCE-MRI clinical validation (PRE / EARLY / LATE + patient-level check)
  → Stratified split 70 / 15 / 15 (train / validation / test)
  → 5-fold cross-validation on TRAIN only
      · candidate backbones: ResNet50 · EfficientNet · MobileViT
      · fold-wise AUC (mean, std), threshold selection
  → Best architecture selected on CV stability
  → Global retrain on TRAIN + VALIDATION (85%)
  → Final holdout TEST (15%) — fully isolated until this step

Model artifacts are exported in a recovery-safe format together with their decision thresholds and consolidated metrics.

Data & split

Breast DCE-MRI regions of interest, indexed with patient-level identifiers to guarantee no patient appears in more than one split. Stratified 70/15/15 partitioning keeps class balance consistent across train, validation, and the final holdout test.

Holdout test result

MetricValue
AUC-ROC0.629 (95% CI 0.42–0.83)
PR-AUC0.709
Balanced accuracy0.629
Sensitivity (recall)0.818
Specificity0.308
F1-score0.735

Preliminary result on a small holdout cohort (n=35 patients) from an early backbone (ResNet18) — reported with its confidence interval intentionally, not as a final clinical claim. Sensitivity is prioritized over specificity, and the target recall threshold has not yet been met, which is exactly what the next iteration of cross-validated architecture comparison is for.

Full evaluation protocol also produces ROC and PR curves, a confusion matrix, a calibration curve, and Grad-CAM visualizations for qualitative review — standard practice for a pipeline meant to be clinically interpretable, not just accurate on paper.

Packaging

Containerized with Docker and deployed to a university-provided server (on loan from a faculty advisor) for testing and thesis demonstration — not a commercial production environment, but a real, running deployment outside the training notebook.

Experiment tracking runs through local MLflow and TensorBoard logs generated during training.

Career Ops — Multi-Agent AI System

AI Systems
LLM Agents · Flask

An intelligent career pipeline: LLM-powered agents read and score job postings against a configurable profile, prioritizing ML/AI-relevant opportunities and filtering out generic listings — with the scoring logic itself defined as auditable configuration, not a hidden prompt.

Stack — LLM orchestration (GPT-4 / Claude / Gemini / DeepSeek via OpenRouter) · RAG · Flask backend

What it does

Agents analyze incoming job postings, score them for ML/AI/backend relevance, and surface prioritized opportunities on an internal dashboard — reducing manual triage during a job search to a review step.

Configuration, not a black box

Priorities and exclusions are declared explicitly (what to prioritize, what to penalize) so the agent's behavior stays legible and adjustable, rather than buried inside an opaque prompt.

Pipeline

Job postings (ingested)
  → Retrieval-augmented context assembly (RAG)
  → LLM agent scoring (role relevance, ML/AI signal)
  → Structured output (auditable, reproducible)
  → Flask API → dashboard

Engineering patterns

Prompt engineering for structured, parseable agent output · retrieval-augmented context instead of relying purely on model memory · multi-model routing across providers via OpenRouter · local experimentation with Ollama.

Private repository — code not public while in active development
